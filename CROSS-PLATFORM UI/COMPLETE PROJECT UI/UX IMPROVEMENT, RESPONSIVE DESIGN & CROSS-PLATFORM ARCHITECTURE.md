# APPROVED IMPLEMENTATION ARCHITECTURE

The following implementation direction is approved as a staged plan. Approval does not mean that native application targets have already been created or verified.

## Platform strategy

- **Web:** Keep the existing Next.js application and its current API routes as the web product and canonical backend. Improve the current UI in place before considering structural migrations.
- **Android and iOS:** Add an Expo / React Native application after the web presentation is stable. Use platform-specific navigation and native controls while sharing only platform-neutral domain and service code.
- **Windows and macOS:** Add a Tauri 2 desktop application with a React frontend. Build a desktop-specific presentation layer rather than loading the website in a WebView. Connect to the same deployed API endpoints.

This approach avoids replacing Next.js or duplicating backend operations. It also avoids forcing web components into native environments. The cost is maintaining web, mobile, and desktop presentation layers, so shared code must remain limited to code that has no browser- or platform-specific assumptions.

## Proposed repository boundaries

Keep the current web application at the repository root during incremental implementation. Introduce these boundaries only after dependency and API-contract mapping:

```text
apps/
  mobile/                 Expo / React Native Android and iOS
  desktop/                Tauri 2 + React desktop UI
packages/
  core/                   Platform-neutral API clients, models, validation,
                          session contracts, and pure domain utilities
  design-tokens/          Brand colors, spacing, type scale, radii, elevation
```

The current Next.js `app/api` handlers remain the canonical server implementation. Existing `crypto-swap` services and route behavior must be mapped before any code is extracted. Shared modules must call the same endpoints and preserve request/response shapes; they must not contain a second implementation of trading, authentication, payment, or transaction rules.

## Platform-specific boundaries

- Keep Next.js App Router navigation and web accessibility behavior in the web application.
- Use Expo Router and native Android/iOS controls in the mobile application.
- Use desktop window, menu, keyboard, and resizing conventions in the Tauri application.
- Put API access behind a shared interface, but provide platform-specific token storage adapters. Web keeps its existing session behavior; native secure-storage integration must be validated without changing server authentication rules.
- Share brand tokens and interaction guidance, not a single UI component tree. Native components should follow Material Design and Apple Human Interface Guidelines where appropriate.
- Treat embedded charts, wallet connections, and other browser-dependent integrations as compatibility gates. Do not substitute static or mock interfaces when an integration is not yet available on a target.

## Controlled implementation and verification

1. Stabilize and verify current web routes, responsive layouts, navigation, localization, and keyboard-accessible dialogs.
2. Audit current API boundaries and isolate pure shared utilities without changing API handlers or business operations.
3. Add the Expo application and validate Android and iOS builds and existing workflows against the current backend.
4. Add the Tauri application and validate Windows and macOS builds, desktop interactions, and existing workflows against the same backend.
5. Mark a platform complete only after its build and relevant integration checks succeed. Record unavailable device or operating-system testing as a limitation.

**Status:** Web UI improvements are being implemented incrementally. The Expo and Tauri targets remain planned and are not represented as implemented or build-verified.
